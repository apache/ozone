# Abstract

Add NFSv4.1 access to selected FILE_SYSTEM_OPTIMIZED (FSO) buckets using NFS-Ganesha and an Ozone File System Abstraction Layer (FSAL). Files remain native Ozone files readable through OzoneFS and supported S3 operations. The first release supports new-file transfers, reads, directory operations, rename, and delete. It does not provide general POSIX file editing.

This proposal supplements the historical [NFS proposal](nfs.md), which selected Hadoop NFSv3. HDDS-3001 is the existing umbrella issue; implementation subtasks need their own HDDS issues before upstream PR submission. This document is a draft, not an accepted OEP or an assertion that NFS is currently supported.

# Requirements

| Area | First production release |
| --- | --- |
| Protocol | NFSv4.1 over TCP through Ganesha; NFSv3, pNFS, and delegations are disabled. |
| Exports | Explicitly configured FSO buckets; no OBS, LEGACY, bucket links, or snapshot exports. |
| Namespace | Export root is a bucket. Volume and bucket administration remain outside NFS. |
| Data | Create new files, transfer their contents, and read existing files. Writes, including append, are allowed only while the active NFS transfer lease owns a file created by that transfer. |
| Namespace mutations | mkdir, rmdir, rename, and remove, subject to Ozone ACLs and active-transfer coordination. |
| Writers | One mutation owner per file, enforced by OM across NFS and other supported clients. |
| Durability | Successful stable WRITE and COMMIT survive loss of the gateway host. |
| Authentication | RPCSEC_GSS with Kerberos user identities; production does not accept AUTH_SYS. |
| Authorization | Each operation is authorized by OM under the mapped Ozone user. |
| Availability | One active gateway per export with restart and fenced replacement. Automatic failover is deferred. |
| Compatibility | Files remain usable through supported OzoneFS and S3 operations. No silent weaker behavior on old OM versions. |

Reject edits to content that predates the active NFS transfer, appending to pre-existing files, arbitrary truncation, hard links, symbolic links, and user-requested POSIX byte-range locks. Preserve NFS OPEN share reservations required by the supported transfer contract. Appending to a file created by the active NFS transfer lease is allowed; creating an empty file and setting its size to zero during that transfer must be distinguished from truncating a pre-existing file. Attribute handling must be tested with actual upload clients; successful mounting alone is insufficient.

Initially use RATIS replication for writable exports. EC write exports remain disabled until synchronization and recovery satisfy the same durability contract. Existing readable files require explicit coverage for the replication configurations advertised by the gateway.

# Architecture

```text
NFS client -- NFSv4.1/RPCSEC_GSS --> Ganesha + FSAL_OZONE
                                              |
                                  authenticated local backend RPC
                                              |
                                    Ozone Java gateway
                                     /              \
                         OM namespace/ACLs       datanode data
```

Ganesha owns the NFS protocol, sessions, replay cache, OPEN state, and protocol recovery. The FSAL translates operations and errors. A separate Java gateway uses Ozone client APIs; it does not read OM RocksDB directly. OM owns durable identities, mutation ownership, and transfer recovery metadata. SCM and datanode responsibilities remain unchanged unless durability experiments establish a missing primitive.

The separate process avoids embedding a JVM in Ganesha. The local channel authenticates the FSAL with mutual TLS and protects asserted user identities; it cannot be an unauthenticated privileged-user proxy. The approved prototype uses a versioned protobuf/gRPC contract and existing Ozone protobuf/gRPC dependencies on the Java side. The optional native dependencies and wire definition are implemented, but throughput and packaging measurements remain required before selecting a supported runtime baseline. JNI remains an alternative if the process boundary cannot meet the transfer target.

Ganesha is an external runtime component. Its license and FSAL distribution arrangement need Apache review; do not copy Ganesha implementation into Apache-licensed source or add it as a mandatory Ozone build dependency. The native integration prototype targets upstream Ganesha V5.7 with its pinned ntirpc submodule. Linux compilation and mounted-client contracts must pass before this becomes the supported runtime baseline.

The current Dockerfile fetches Ganesha at a pinned upstream commit and builds a separate runtime image; it does not add Ganesha to the Ozone Maven or distribution artifacts. The Ozone source does include patches applied to Ganesha and an FSAL intended to be built and loaded with that runtime. The PMC and Legal Affairs Committee must review whether this compatibility source and the proposed image workflow fit the optional-feature boundary and what notices or source obligations apply. # Approved FSAL-to-Java transport

The user approved this transport and its optional native gRPC C++/protobuf dependencies on 2026-10-08. The shared versioned proto, Java loopback mutual-TLS listener, certificate-fingerprint/export allowlist, and optional C++ adapter are implemented. The Java gateway now dispatches MKDIR, REMOVE, and RENAME through the authorized Ozone client path; the native adapter and Ganesha FSAL callbacks carry those operations, and CREATE is advertised only when the export lease manager is configured. Focused service tests cover mutation dispatch and capability negotiation. The FSAL must compile against patched Ganesha V5.7 and pass mounted mutation, file-transfer, and crash-recovery acceptance before these operations are treated as production-ready. Use a dedicated protobuf/gRPC service over mutually authenticated TLS between the native FSAL and the Java gateway. Bind to loopback for the initial single-host deployment. Require client certificates even on loopback, verify the backend server name, and authorize the authenticated gateway certificate against an explicit export allowlist. A certificate accepted by the CA does not automatically grant access to every export or permission to impersonate users. Operator-provided certificate/key/trust files and the Java gateway's Kerberos keytab remain separate credentials.

The native FSAL uses a small C++ gRPC adapter behind a C ABI; its public Ganesha callbacks remain C. This adds the native gRPC C++ and protobuf libraries plus the matching code-generation tools to the optional NFS build, while Java reuses Ozone's existing protobuf/gRPC dependencies. Do not link C++ generated protobuf code against a different protobuf runtime or share native C++ ABI types across the FSAL adapter boundary. The existing standalone C handle codec remains buildable without gRPC or Ganesha. Pin and verify the native toolchain in the Linux build image before making it a supported baseline.

This choice uses generated cross-language messages, TLS authentication, deadlines, cancellation, and bounded messages. Its cost is a C++ runtime/toolchain and additional packaging. A custom TLS-framed protocol avoids gRPC C++ but would require maintaining framing, evolution, cancellation, flow control, and cross-language encoding ourselves; it is the fallback if measured gRPC overhead or packaging constraints rule out this proposal. Hadoop RPC directly from the FSAL would require a native Hadoop/SASL/protobuf client implementation and is not the preferred first integration.

For each client operation, copy the authenticated Kerberos principal from Ganesha's RPCSEC_GSS request context, preserve its exact bytes, and pass the GSS service level. The V5.7 source review found that an ordinary FSAL callback receives `op_ctx`, whose `creds` contain mapped UID/GID values but not the RPC request or principal. The principal and GSS service are in `svc_rpc_gss_data`, reached through `svc_req.rq_auth`; the NFSv4 compound retains that request credential separately. Therefore an out-of-tree FSAL cannot safely recover the principal through the documented `req_op_context` API. The pinned-source patch now copies the authenticated principal bytes and GSS service into the operation context for the lifetime of the request. The callback source requires the Kerberos V5 mechanism OID, a bounded principal, and integrity or privacy protection; absence of a GSS identity is denied. Do not read undocumented thread-local or TI-RPC internals from the FSAL, and never reconstruct a principal from a UID. Linux/aarch64 mounted contracts verify the RPCSEC_GSS identity reaches the Java fixture and that reads and writes publish real Ozone data through an NFSv4.1 export. On 2026-10-14, a secure mounted Linux client reclaimed an open file across replacement Ganesha containers with different hostnames, the same NFS address, stable node ID, server scope and owner, and a shared `RecoveryRoot`; read, append, fsync, and byte-exact final contents passed. The replacement Java gateway used a distinct configured gateway ID and waited for the prior OM export lease to expire before serving. This ran on one Docker host with a bind-mounted recovery directory, so separate physical hosts and remote shared-storage behavior remain acceptance gates. Pinned V5.7 `fs_ng` uses `RecoveryRoot/RecoveryDir/node<N>` when `Clustered` is true; `-I <N>` selects that numeric node ID, and a replacement starting with the same ID reads that node's current recovery link. This is a candidate for fenced active/passive host replacement when both hosts use the same durable `RecoveryRoot`, stable export identity, node ID, server scope and owner, and NFS address. The Java gateway is loopback-only and holds the OM export lease, so the replacement host must start its own gateway and acquire that lease before serving. This container-level changed-hostname contract verifies both Ganesha state reclaim and gateway lease takeover with distinct gateway IDs; separate physical hosts and remote shared-storage behavior remain acceptance gates. The `fs_ng` takeover-event reader is disabled in V5.7, so this does not support concurrent active/active operation. Internal root construction may use the configured binding; it must not authorize client metadata or data access without a caller context.

The Java interceptor validates the TLS peer before accepting per-call identities. Map the principal with the configured Hadoop Kerberos name rules, create a proxy UGI with the logged-in Java gateway as its real user, and apply existing Hadoop proxy-user authorization. OM independently applies its proxy-user and ACL checks. Construct and use Ozone clients under the proxy UGI; never reuse a service-user client for caller operations. Any future per-user client cache must be bounded, keyed by authenticated identity, and closed on eviction. The gateway host/address used for proxy authorization comes from the authenticated channel and configured topology, not from a client-supplied address. User-presented principals are not bearer tokens: only the explicitly trusted Ganesha peer may assert them.

Add a versioned capability request before exports become usable. It validates the persistent export UUID, trusted connected cluster ID, volume/bucket incarnation, native FSO layout, and persisted index readiness. The gateway advertises CREATE only when its export lease manager is configured. Mounted writes, Ozone publication, and replacement-container reclaim with persisted Ganesha recovery state now pass, including a changed-hostname container replacement; production enablement remains gated on separate-host shared-storage recovery and the remaining acceptance criteria. Unsupported service versions or old OM capabilities fail closed, with no pathname fallback.

The first service contract contains capability, handle lookup/getattr, child lookup, bounded readdir, and ranged read. Start with a maximum 1 MiB read payload, 256 entries per directory page, 1024 UTF-8 bytes per principal, and a 4 MiB transport message limit; make operational limits configurable within hard protocol bounds. Use the existing NFS status values for backend errors and gRPC status for transport failures. A timeout or disconnect never implies successful mutation. Deadlines, cancellation, concurrency bounds, and backend latency/error metrics are required before mounted workloads. The Java gateway now exports per-operation RPC counts, average latency, NFS status errors, and gRPC failures through Ozone Metrics2 without caller or export labels.

Validation must include C++/Java TLS interoperation, untrusted/missing/wrong-export certificates, two Kerberos principals with different ACLs, denied proxy rules, unmappable principals, AUTH_SYS rejection, expired credentials, oversized requests, unsupported capabilities, and connection cancellation. The mounted Linux contract must use the real FSAL with RPCSEC_GSS; the existing MEM/AUTH_SYS smoke test cannot establish these properties. References: [gRPC authentication](https://grpc.io/docs/guides/auth/), [Ganesha V5.7 FSAL context](https://github.com/nfs-ganesha/nfs-ganesha/blob/V5.7/src/include/fsal_api.h), and [Ganesha V5.7 RPC credential handling](https://github.com/nfs-ganesha/nfs-ganesha/blob/V5.7/src/support/nfs_creds.c).

# Durable file handles

Paths and metadata update IDs are not file identities. A file handle uses an export UUID, volume ID, bucket ID, object ID, and object kind. The export UUID binds to a specific Ozone cluster and bucket incarnation in persistent export configuration. Replacement gateways reuse that binding. The Java `NfsExportBinding` value now validates export UUID, connected cluster ID, volume/bucket IDs, and root kind before OM lookup. Its loader requires all six named `ozone.nfs.export.<name>.*` properties from operator-persisted Ozone configuration, with no generated UUID or default incarnation. IDs use unsigned decimal notation. Tests cover missing and malformed configuration, cross-cluster/export/incarnation rejection, and replacement root continuity. The binding value itself does not implement transport authentication or cluster discovery; `NfsGatewayDaemon` performs TLS peer authorization and obtains the live cluster ID from SCM before constructing readers. Remapping an export to another cluster or bucket requires a new UUID.

The initial backend payload is 48 bytes, in network byte order:

| Offset | Bytes | Field |
| --- | --- | --- |
| 0 | 4 | Magic `OZNF` |
| 4 | 1 | Format version, initially 1 |
| 5 | 1 | Kind: 1 bucket root, 2 directory, 3 file |
| 6 | 2 | Reserved, zero |
| 8 | 16 | Export UUID, most significant bits followed by least significant bits |
| 24 | 8 | Volume object ID |
| 32 | 8 | Bucket object ID |
| 40 | 8 | Object ID; bucket ID for bucket root |

Identifiers preserve their complete 64-bit representation, including Ozone epoch bits. Ganesha may wrap this payload; verify the final handle against the NFSv4 limit. Invalid encoding maps to BADHANDLE; a valid handle for an absent object maps to STALE. An unknown or mismatched export binding must not resolve into another export. Handles are identifiers, not authorization credentials: every operation still needs ACL checks.

FSO tables are indexed by volume, bucket, parent object ID, and name. An object ID cannot currently serve as an efficient general reverse lookup. Add an OM-maintained object-ID lookup only after review of its schema, lifecycle, bootstrap, and upgrade behavior. Rename must preserve identity and update resolution atomically. Delete must invalidate resolution; recreation at the same path must not reuse the old identity. Parent-directory rename must preserve descendant handles.

The FSAL retains the canonical 48-byte encoding for wire, host, and MDCACHE key representations. It must not expose a native C struct as a cache key, since padding and host byte order are not stable identities. `wire_to_host` validates the payload without changing its byte representation; `host_to_key` and `handle_to_key` use the same complete payload, including export UUID. This satisfies Ganesha's documented handle-conversion invariant and keeps separate export bindings distinct in the cache. `create_handle` validates the export binding and invokes authorized OM identity lookup; syntactic decoding alone does not establish object existence. See the [upstream FSAL API contract](https://github.com/nfs-ganesha/nfs-ganesha/blob/V5.7/src/include/fsal_api.h).

The first code milestone implements the payload codec and tests the underlying FSO identity assumptions. It does not claim to implement reverse lookup or stale-handle resolution.

# Backend error contract

Translate OM failures by result code, not message text. Keep missing-name lookup distinct from persistent-handle resolution: a missing child is NOENT, while an absent object referenced by a valid handle is STALE. Malformed handle payloads are BADHANDLE. Do not turn any OM exception, including one carrying OK, into a successful response.

| Backend condition | Error category |
| --- | --- |
| Missing volume, bucket, file, or directory during name lookup | NOENT |
| The same missing object during persistent-handle resolution | STALE |
| Ozone ACL, identity, or credential rejection | ACCESS |
| Existing file or directory during exclusive creation | EXIST |
| File lookup identifies a directory | ISDIR |
| Invalid backend request, key name, or path | INVAL |
| Nonempty directory removal | NOTEMPTY |
| Ozone quota exceeded | DQUOT |
| Unsupported operation, disabled feature, or unfinalized required feature | NOTSUPP |
| OM initializing/prepared, SCM safe mode, or pending lease recovery | DELAY |
| Rename rejected because the file is open | FILE_OPEN |
| Other OM failures | IO |

These categories use explicit values from [RFC 8881 section 15.1](https://www.rfc-editor.org/rfc/rfc8881.html#section-15.1), not Java or OM enum ordinals. Ganesha remains responsible for the final operation-specific error response and NFS session state. In particular, expired Ozone credentials must not be reported as an expired NFS lease, and backend failures must not invent NFS state-ID errors. Context describes the individual lookup that failed: LOOKUP can encounter a stale parent handle and a missing child name in the same request path.

The Java error contract has unit coverage for known mappings and a no-success/no-session-error invariant over every OM result code. The existing FSO integration test checks categories against actual OM missing-file and directory-lookup failures. This does not establish that a running Ganesha FSAL already consumes these categories.

# Approved OM identity lookup design

The user approved the new `nfsObjectTable`, additive `LookupNfsObject` request, and associated upgrade/bootstrap gates on 2026-10-07. This satisfies AGENTS.md's Ask First rule for this proposal. The persisted index-value message, codec, and OM table registration are implemented. OM layout version 12 gates index maintenance; shared file commit/hsync and multipart completion helpers update the pointer in their cache transaction and database batch. Explicit mkdir and implicit parent creation now use the same cache and database transactions for directory pointers. File and directory rename now update the same identity pointer in their cache transaction and database batch; ancestor rename leaves descendant pointers unchanged. Single and bulk deletion tombstone identity pointers in the canonical cache transaction and remove them in the database batch. Directory purge invalidates live descendant pointers alongside the live canonical records, including when deletion metadata moves into a snapshot; snapshot index copies remain untouched. File commit now invalidates a replaced object ID using the identity captured by the request, including consecutive overwrites in one database batch. Multipart completion retains the existing canonical object ID on overwrite; targeted tests now verify the cache and persisted pointer across two uploads. Lease recovery initiation changes open-file metadata; final recovery commits use the same indexed file-commit path. The readiness predicate now requires finalized layout support and a persisted completion marker matching index layout version 12; cache-only, aborted, missing, or malformed markers cannot enable it. An additive internal bootstrap request now revalidates scanned identities under the bucket lock, writes bounded index batches with progress, and atomically persists final readiness through its OM response. The leader-side scanner now runs as an opt-in background service, waits for a replicated initialization barrier to reach RocksDB, resumes persisted cursors, and completes directory/file phases through Ratis. Its unit coverage includes a delayed initialization batch and service replacement across a 500-record boundary; the shared FSO integration contract now reaches persisted readiness through the real Ratis path before exercising multipart overwrite, rename, and deletion. The three-OM HA integration test now interrupts bootstrap after a 500-record directory batch, changes the namespace under a replacement leader, resumes to persisted readiness, and verifies all 506 live entries on every OM after the old leader restarts. The server-side identity resolver validates the volume/bucket incarnation, indexed object kind, canonical row, and every directory ancestor under the bucket read lock. The metadata reader checks caller ACLs on the resolved object before returning status or authorized file block information; targeted tests cover stale or malformed namespace identities and two proxy users with different key permissions. ACL request contexts retain each effective caller and the real gateway user; the denied caller receives neither status nor block lookup. This unit evidence does not establish RPCSEC_GSS authentication or proxy-user authorization at the network boundary. The 19 resolver cases also verify unsupported bucket links, OBS layout, snapshot roots/descendants, stale volume and bucket incarnations, missing live volume/bucket metadata, and incorrect root kinds. The additive `LookupNfsObject` wire RPC (type 159, request field 161, response field 159) and client translator are implemented. The wire kind explicitly uses bucket 1, directory 2, and file 3; IDs preserve their complete uint64 bit patterns. The request carries no path. This read is routed to the leader, and the client fails closed when a response lacks the lookup capability. Common tests cover all three wire kinds, request validation, unsupported responses, and leader routing. The shared FSO integration contract now calls the translator over Hadoop RPC and verifies bootstrap gating, file block locations, head-only responses, root/directory identities, rename continuity, and stale handles after recreation. Gateway integration remains unfinished. Partial index maintenance does not enable NFS lookup or exports.

## Proposed atomic child lookup and directory paging (approval needed)

The current `LookupNfsObject` resolves one persistent object handle; it cannot resolve a child name relative to a directory handle or enumerate entries. Splitting parent validation and child lookup into separate OM calls would allow rename/delete/recreation to redirect a lookup between calls. Directory paging also needs a mutation verifier so clients restart instead of skipping or repeating entries after a concurrent namespace change.

The additive OM protocol command `LookupNfsChildren` (type 160; request field 162; response field 160) is implemented. The request identifies the volume, bucket, parent object, and parent kind (`BUCKET` or `DIRECTORY`). A child lookup supplies `name` and omits paging fields. A page request supplies `maxEntries` (1 through 256); subsequent pages supply `startAfterObjectID` and `verifier` together. OM resolves the object ID through `nfsObjectTable` to recover the canonical child name and continue the existing name-sorted iterator. The response contains child `OzoneFileStatusProto` values, the current parent verifier, and `eof`. A missing child maps to `NOENT`; a stale cursor or changed verifier maps to NFSv4 `BAD_COOKIE`. Old OMs do not implement this command, so the gateway treats a missing response as unsupported and does not fall back to pathname lookup.

OM validates the live FSO bucket and parent handle, resolves its current path through `nfsObjectTable`, checks the caller's existing lookup/list ACL, and obtains a sorted bounded page while holding the same bucket read lock. The parent identity and ACL must be checked inside that operation; the Java gateway must never perform `getattr(parent)`, then `lookup(name)` or `readdir` in a separate RPC. The first page returns the parent's existing persistent `updateID` as its verifier. Later pages must present the same verifier or receive `BAD_COOKIE`. Exact child lookup returns the child's status and identity in this same atomic operation.

For this proposal, direct-child membership changes advance the existing parent record's `updateID` in the same cache transaction and database batch as the canonical namespace change: directory and implicit-parent creation, publication of a new file, removal of files/directories (including bulk delete), and rename of a child. A same-parent rename advances it once; cross-parent rename advances both parents. Content-only writes that preserve the same file identity and name do not affect the directory verifier. The bucket record supplies the verifier for the export root. This reuses existing `OmDirectoryInfo` and `OmBucketInfo` fields; the proposal adds no table, column family, or layout version. Tests must prove every FSO mutation path updates the parent verifier atomically and that a page cursor from before a mutation is rejected. If Ozone's existing `updateID` cannot safely carry this namespace generation across cache/Ratis ordering, stop and revise the design before implementing pages.

The Java gateway adds bounded `LOOKUP` and `READDIR` handlers over this one OM call. NFSv4 exposes directory cookies as 64-bit values, so the adapter encodes the stable child object ID plus three (reserving cookie values 0, 1, and 2) and sends that ID with the updateID verifier. OM resolves the ID to its indexed name, preserving the name-sorted order without a process-local cookie cache. The verifier changes with parent membership mutations.

This is a design proposal, not an approved wire or OM mutation change. It requires review under the repository's Ask First rule for protobuf/RPC compatibility and stored namespace metadata behavior.

The index key is `(volume object ID, bucket object ID, object ID)`. Its value contains object kind, parent object ID, and the final path component. It contains no ACLs, block locations, or cached full path: those remain in the canonical FSO tables. Use the existing protobuf codec and an explicit message for the value rather than delimiter-encoded metadata. Bucket roots are validated using the bucket table and do not need index rows.

FSO mutations maintain index rows in the same OM cache transaction and RocksDB batch as their canonical records. Cover implicit parent creation, explicit mkdir, file commit and hsync, multipart completion, file and directory rename, single/bulk delete, and directory purge. Ancestor rename updates only that directory's parent/name record; descendant handles retain their object IDs. Deletion invalidates the corresponding index row. Uncommitted uploads cannot issue a resolvable persistent handle until their native identity exists under the transfer contract.

`LookupNfsObject` accepts volume/bucket names, the expected volume/bucket object IDs, the object ID, and the expected kind. The Java gateway first validates the handle's export UUID against its persistent export binding; the OM operation additionally validates bucket incarnation and FSO layout. A valid handle is not a credential. Only the live namespace is supported; reject links and snapshot paths explicitly.

Within the existing bucket read lock, resolve the object and its ancestor chain, verify each index row against the canonical record, enforce the existing Ozone ACL checks under the authenticated caller, and return authoritative status. Files also return the authorized block information through the existing lookup machinery. Do not return a path and then reopen that path in a second request: rename/delete/recreate between those calls could read a different object. Invalid or inconsistent index rows must not resolve to a different object.

Introduce an OM layout feature for the index. Before finalization, reject the new operation and keep exports disabled. After finalization, mutations maintain the index; exports remain disabled until a resumable bootstrap has completed. Before scanning persisted canonical tables, bootstrap submits an empty initialization batch through OM/Ratis and waits for its `1:` progress marker to reach RocksDB. This provides a persistence barrier behind all earlier canonical mutations, including pre-finalization writes queued in the double buffer. A fresh cluster may have no `#LAYOUTVERSION` database row, so that row cannot be the sole barrier. The replicated initialization request is permitted only after index maintenance is enabled; other bootstrap requests require existing progress. Backfill requests run through OM/Ratis and validate the current canonical identity before adding rows, so a stale source scan cannot resurrect deleted objects or overwrite a newer rename. Store bootstrap progress/readiness in OM's existing metadata table. The completion key is `#NFSOBJECTINDEXREADY`, with value `12` for the index layout feature. Only the final replicated bootstrap response may persist that value, atomically with its final index rows; the readiness predicate bypasses the cache so an unapplied completion batch cannot enable lookup. Bootstrap uses the internal `BootstrapNfsObjectIndex` command (type 158); normal client `preExecute` rejects it. Each batch contains at most 500 candidate object IDs from one bucket, a directory/file phase, and expected/next scan cursors. Candidate keys and cursors use RocksDB's unsigned encoded-byte ordering. OM validates the expected progress and current volume/bucket identities, ignores candidates that have been renamed, deleted, or recreated, and derives parent/name from the current canonical row. Progress is `1:<cursor>` for directories, `2:<cursor>` for files, and `DONE` after the file scan; progress and accepted rows share a cache transaction and database batch. The trusted leader-side scanner must establish scan exhaustion before submitting a phase-completion batch. `NfsObjectIndexBootstrapService` scans persisted directory and file tables in their encoded key order, processes one bucket per batch, and waits for each progress update to be persisted before continuing. It loads the preexisting FSO bucket identities after the initialization barrier; newly created buckets already maintain their index. Missing bucket IDs are skipped, and OM revalidates mapped bucket names/IDs before accepting pointers. Enable the service with `ozone.om.nfs.object.index.bootstrap.enabled=true`; it defaults to false during development. The batch interval is `ozone.om.nfs.object.index.bootstrap.interval` (default `1s`). KeyManager starts and stops it with its other background services. It runs only on the ready leader and stops submitting requests after readiness is persisted. Tests must interrupt bootstrap, mutate files during it, and restart or fail over OM before declaring readiness.

New protobuf fields/messages and request type values are additive. Capability negotiation must fail closed with an old OM: the gateway cannot fall back to pathname handles or silently accept unindexed lookups. Operational rollback to an OM version without this feature requires disabling NFS exports and follows the existing finalized-layout rollback restrictions. Snapshot exports remain excluded; existing snapshot create/delete/purge must continue to work with the added column family.

The index adds metadata per native FSO object. Measure size and write amplification before release. This proposal approves the table and lookup capability; it does not presume that global indexing overhead or bootstrap throughput is acceptable without measurement.

# New-file transfer semantics

A new transfer obtains exclusive mutation ownership through OM and creates one native FSO file identity. Retries with the same operation identity must not create duplicate files. Other clients may read synchronized content, but conflicting create, overwrite, rename, or delete operations must be rejected or serialized under the same OM ownership rules.

First evaluate direct streaming: buffer a bounded amount of out-of-order data, stream the contiguous prefix, and synchronize data and recoverable OM metadata before stable acknowledgments. A duplicate write with identical bytes is idempotent. Do not mistake a small reorder window for arbitrary random-write support; use durable range staging when NFS clients can overwrite already accepted bytes.

The current Ozone client path is sequential: `RpcClient.createNfsFile` returns an `OzoneOutputStream` backed by `KeyOutputStream`, and `hsync` is supported only for RATIS replication. The bounded reorder buffer retains a contiguous prefix until the caller confirms the Ozone write succeeded; if the output stream fails, the transfer must be aborted because the accepted prefix may be ambiguous. This is sufficient to test contiguous-prefix streaming, but does not itself provide arbitrary-offset replacement or stable acknowledgment beyond a gap. The gateway prototype must prove the direct-stream limits with concurrent and reordered WRITE tests before treating it as a complete transfer path.

NFS may request a stable write beyond an unresolved hole. The prototype must establish whether direct streaming can satisfy that request without deadlock or data loss. If it cannot, add durable Ozone-backed staging with byte-range coverage and replay information. Accepted stable ranges must be recoverable after host loss even before the final file is assembled. Publication must preserve the already-issued file identity, and reads must reflect the documented accepted ranges. A staging design that creates a new visible object ID on close is unacceptable.

### Durable range staging proposal

Direct streaming cannot acknowledge a stable write beyond the current contiguous prefix. The approved fallback is to persist each noncontiguous range as an immutable internal Ozone staging object and record it in a new OM `nfsTransferRangeTable`. The row is keyed by export UUID, file object ID, file-lease generation, starting offset, and staging object identity; it records the byte length, SHA-256 checksum, staging key, transfer ID, and OM Ratis transaction index. Rows at the same offset remain available so a shorter later write does not discard the earlier tail. Reads and assembly apply ranges in transaction order, giving later writes last-write-wins behavior. Exact retries reuse the immutable staging object and manifest row. Staging objects live in an OM-managed NFS system bucket outside the exported user bucket, so OzoneFS/S3 listings and NFS directory reads never expose them. The schema is introduced at OM layout version 14.

For a stable WRITE, the gateway writes and closes the staging object first, then submits an OM transaction that validates the current export and file lease and records the durable range. It replies stable only after both operations succeed. A crash between object close and manifest insertion leaves an unreferenced staging object for expiry cleanup; a crash after insertion leaves enough OM metadata to recover the bytes. Exact retries with the same range and checksum are idempotent. Different writes may overlap; OM's Ratis transaction order determines which bytes win, including writes at the same offset with different lengths or checksums.

Reads during an active transfer combine the committed contiguous prefix with staged ranges and return zeroes for uncovered sparse holes. On successful CLOSE, the gateway assembles the full byte stream in offset order into the original OM-created open key, filling uncovered holes with zeroes, synchronizes it, and commits it without changing its object ID. Only after the target key is committed does OM remove the range manifest and staging objects. If assembly fails, the file lease and staged ranges remain recoverable; CLOSE does not report success. Expired transfer recovery fences the old gateway before a replacement resumes assembly.

This makes stable ranges recoverable and keeps staging names outside user namespaces, at the cost of a new OM layout version, range-manifest transactions, internal staging-bucket lifecycle, an extra Ozone write/read for noncontiguous data, and read overlay logic. The alternative is to reject or indefinitely delay stable writes that cross holes, which avoids schema and extra I/O but does not provide usable sparse or random-offset file creation. The user approved implementing the table, internal staging bucket, and RPCs. The table, codec, OM range mutations, and fenced gateway submission path are implemented. The gateway writes deterministic immutable range objects to a separately configured private FSO bucket and verifies byte-identical retries before submitting their manifest; OM retains overlapping rows and returns their Ratis transaction indexes. Unit tests cover same-offset rewrites, overlapping byte ranges, idempotent retries, and the gateway read overlay applying newer writes last. Later accepted ranges replace earlier bytes according to OM Ratis transaction order, including writes that overlap or reuse an offset with a different length. The FSO MiniOzoneCluster contract creates a separate native-FSO staging bucket, writes and reads back the range object, records its qualified locator in the OM manifest, and removes the manifest before deleting the staged file. This validates real Ozone storage and OM reference ordering, but does not exercise the production staging helper against a MiniOzoneCluster. The gateway resolves RATIS replication from each bucket's default, then the gateway's configured RATIS factor, with Ozone's RATIS/THREE default as the final fallback; EC writes fail closed. Closing each immutable range object before recording its OM manifest makes acknowledged `FILE_SYNC` data recoverable. The published file is closed under its current OM fence before final COMMIT succeeds. The Java gateway dispatches bounded WRITE requests, persists each range before replying `FILE_SYNC`, enforces the active file lease's object and Kerberos principal, and serves read-your-writes from staged ranges with zero-filled holes. OM records whether publication reached the canonical key in the same transaction as the key commit, so recovery can distinguish staged data from a published file. The OM lease persists the authenticated owner principal for recovery authorization; takeover fences the old gateway by advancing the file-lease generation and rotating its owner token, and verifies the caller against the recorded owner. WRITE can recover the current lease from a persistent file handle without a transfer ID. The C++ adapter and Ganesha callbacks now dispatch CREATE, MKDIR, REMOVE, RENAME, WRITE, COMMIT, and final close. Mounted mutation, publication, and crash-recovery validation remain outstanding.

UNSTABLE writes may be held in bounded memory. Restart changes the write verifier so clients know to resend uncommitted writes. FILE_SYNC and COMMIT acknowledge only recoverable Ozone data and metadata, never a local-only spool. Ganesha and FSAL error handling must not upgrade an unstable backend response to stable success.

Transfer limits, backpressure, maximum outstanding ranges, and cleanup retention must be configurable. Expiry cannot discard acknowledged stable data. Failed or abandoned transfers retain their recoverable prefix/ranges according to an explicit recovery policy; no successful CLOSE is reported if final persistence fails.

# Cross-protocol ownership and coherence

Current optimistic generation checks are not exclusive writer leases. Inspect all FSO create/open, commit, rename, and delete paths, including OzoneFS and supported S3 requests. Implement ownership in OM's replicated state, with fencing against a displaced gateway. Do not rely on a gateway-local mutex or a convention that other clients will refrain from writing.

OPEN state and Ozone transfer ownership must have explicit acquisition, renewal, recovery, release, and expiry behavior. A commit from a fenced owner fails. Parent-directory operations must also account for active descendant transfers. Owner expiry and reclaim cannot allow an old writer to continue committing.

The current implementation atomically creates a new FSO file and its OM-owned lease. The client retains the returned fence in the open-key session and sends it with commit and hsync; OM rejects regular-client delete, rename, and overwrite while a file lease is active. The FSO mini-cluster contract writes to datanodes through this path, reads the committed bytes, and verifies file and ancestor-directory rename/delete fencing. The gateway now owns transfer leases, stages durable NFS WRITE ranges, recovers ownership after restart, and overlays staged reads. OM also rejects FSO ancestor directory rename and recursive delete while any descendant file has an active NFS writer lease. The Linux/aarch64 mounted Ganesha contract covers file rename plus directory create/remove against the Java fixture; this does not verify mounted publication into real Ozone or crash durability. NFS writes remain a prototype until those real-cluster mounted acceptance gates pass.

### Proposed OM ownership protocol

Before implementing writable exports, add an OM-owned export lease keyed by export UUID and a file-transfer lease keyed by `(volumeID, bucketID, objectID)`. The export lease has a gateway incarnation, fencing generation, and server-assigned expiry. The file lease has the export UUID, transfer ID, opaque owner token, file fencing generation, and expiry. OM grants tokens and generations; clients cannot choose or advance them. Read operations do not require a lease. The first writable scope is a new file only: creating the file identity and acquiring its lease must be one OM transaction, so another client cannot mutate the file between creation and ownership acquisition. Opening a pre-existing file for write, appending to pre-existing content, or truncating a pre-existing file remains rejected; the lease owner may continue writing or append to the newly created file until the transfer is committed and closed.

Renewal and release are conditional on the exact lease identity and fencing generation. Expiry/reclaim increments the generation before another owner can write. Each `KEY_COMMIT`, hsync/stable write, rename, and delete checks the current lease in the same OM transaction that changes the canonical FSO record; NFS writes must present the current OM-issued owner token and generation. OzoneFS and S3 requests without that context fail with `FILE_OPEN` while the lease is active. Directory rename/delete must also reject when any descendant has an active transfer. Reads remain available for the last committed content; uncommitted ranges are private to the active writer until the publication contract says otherwise.

The lease table, file identity row, canonical key metadata, and fencing checks must use the same replicated OM state and transaction boundary. Gateway-local locks, Ganesha OPEN state, and a gateway-supplied timestamp are not authority. OM stamps each lease-changing or guarded mutation request with leader time before Ratis replication; that timestamp is part of the replicated request, so every OM applies the same expiry decision. Configure a maximum OM clock skew and add that grace to expiry before takeover. A gateway restart or replacement must obtain a higher active-gateway generation through OM before reclaiming file leases. Each guarded mutation checks both gateway and file generations, so a stale gateway or owner cannot commit after takeover. The final lease release happens only after stable data and file metadata are committed.

The implementation proposal is an additive internal OM API for export lease acquisition, atomic new-file-and-lease creation, conditional renewal/release, and an owner context on write/commit operations, plus checks on existing OzoneFS/S3 mutation paths. Use an explicit OM result for a conflicting live lease and map it to NFS `FILE_OPEN`; do not overload `FILE_ALREADY_EXISTS`. A disconnected writer retains its lease until expiry, and acknowledged stable ranges must already be recoverable before expiry/reclaim. Add upgrade/finalization gates so old OMs reject writable export capabilities. The user approved this prototype protocol on 2026-10-10; that approval does not imply ASF OEP acceptance.

The first implementation slice adds OM layout feature version 13, an export lease table keyed by export UUID, and a file lease table keyed by native FSO object identity. Export records bind the UUID to the volume and bucket incarnation; file records also carry the transfer ID and opaque owner token. Lease RPCs, FSO mutation fencing, gateway lease management, durable range staging, and restart recovery are implemented as prototypes. The gateway can now publish staged ranges into the existing canonical file under the OM fence; final close removes range manifests and staging objects before releasing the lease. OM records whether canonical content has been published in the same transaction as the key commit. Recovery then reads the canonical file and cleans remaining staged ranges without replaying them, so a gateway crash during close cannot overwrite committed bytes with a partial manifest. Mounted writes, Ozone publication, and changed-hostname replacement-container reclaim with persisted Ganesha recovery state are verified; separate-host shared-storage recovery remains a production gate.
